# CHECKPOINT-002.md

# Checkpoint de Redefinición del MVP

**Proyecto:** Etiquetas

**Versión del Proyecto:** Pre-MVP

**Fecha:** 2026-07-25

---

# Motivo del Checkpoint

Durante la definición de las Historias de Usuario se replanteó el enfoque principal del producto.

Se identificó que el objetivo real del usuario no es administrar un catálogo de productos, sino generar etiquetas de forma rápida a partir de información que ya existe en otras herramientas, principalmente hojas de cálculo.

Esta decisión redefine el alcance funcional del MVP y servirá como referencia para la actualización de la documentación.

---

# Nueva Visión del Producto

El propósito del sistema es permitir que un usuario:

* seleccione una plantilla de etiquetas;
* pegue información proveniente de Excel, CSV u otra fuente de texto;
* permita que el sistema interprete automáticamente esos datos;
* genere una vista previa de las etiquetas;
* imprima las etiquetas.

El sistema actúa como un **transformador de datos hacia etiquetas**, no como un sistema de administración de productos.

---

# Principio Fundamental del MVP

El MVP debe minimizar la cantidad de pasos que realiza el usuario.

El flujo ideal es:

Seleccionar plantilla

↓

Pegar información

↓

Interpretar datos

↓

Vista previa

↓

Imprimir

Todo aquello que no contribuya directamente a este flujo quedará fuera del MVP.

---

# Cambio de Enfoque

## Antes

El proyecto estaba orientado a:

* Gestión de Productos.
* CRUD de Productos.
* Generaciones.
* Etiquetas.
* Impresión.

La administración de productos era el centro del sistema.

---

## Ahora

El proyecto estará orientado a:

* Interpretación de datos.
* Aplicación de plantillas.
* Generación de etiquetas.
* Impresión.

Los datos representan una entrada temporal del proceso y no requieren ser administrados mediante formularios.

---

# Fuente de los Datos

El sistema deberá aceptar información proveniente de diferentes orígenes, por ejemplo:

* Texto copiado desde Excel.
* Texto copiado desde Google Sheets.
* Archivos CSV (en versiones posteriores o si se incluye en el MVP).
* Texto separado por tabulaciones o comas.

La experiencia principal será pegar directamente el contenido en una única área de texto.

---

# Experiencia de Usuario

La interfaz debe priorizar la rapidez.

Se evita el uso de formularios extensos para registrar productos uno por uno.

El usuario podrá corregir la información directamente sobre el texto pegado antes de procesarlo.

---

# Alcance del MVP

El MVP deberá enfocarse exclusivamente en:

* Seleccionar una plantilla.
* Pegar datos.
* Interpretar la información.
* Detectar errores de formato.
* Mostrar una vista previa.
* Generar etiquetas.
* Imprimir etiquetas.

---

# Funcionalidades que salen del MVP

A partir de esta redefinición dejan de ser parte del alcance principal:

* CRUD completo de productos.
* Administración permanente de productos.
* Búsquedas de productos.
* Edición mediante formularios.
* Catálogo de productos persistente.

Estas funcionalidades podrán evaluarse para versiones futuras si existe una necesidad real.

# Decisión de Diseño

Se adopta el siguiente principio para el desarrollo del proyecto:

> **El usuario ya posee la información. La aplicación no debe obligarlo a volver a escribirla; debe convertirla en etiquetas de la forma más rápida y sencilla posible.**

Todas las decisiones futuras del proyecto deberán respetar este principio.

---

# Estado del Proyecto

El proyecto mantiene su metodología **Spec Driven Development (SDD)**.

Antes de iniciar el desarrollo se realizará una refactorización de la documentación funcional para alinearla con la nueva visión del producto.

Una vez finalizada dicha actualización, se retomará la creación de las Historias de Usuario y posteriormente las especificaciones técnicas (Specs), asegurando que toda la documentación sea consistente con el propósito real del MVP.
